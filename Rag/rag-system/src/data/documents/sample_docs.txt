== Retrieval-Augmented Generation (RAG) ==

Retrieval-Augmented Generation (RAG) is a technique that enhances large language models (LLMs) by
connecting them to an external knowledge base at inference time. Instead of relying solely on the
knowledge baked into the model's weights during training, RAG retrieves relevant passages from a
vector store and includes them as context in the prompt. This allows the system to answer questions
about domain-specific or up-to-date information without expensive fine-tuning.

The core RAG pipeline has five stages:
1. Embed the user's query into a dense vector using the same embedding model used at ingestion time.
2. Retrieve the top-k most semantically similar chunks from the vector store.
3. Format the retrieved chunks into a context string.
4. Build a prompt that instructs the LLM to answer using only the provided context.
5. Call the LLM and return the answer together with the source references.

== Vector Databases ==

A vector database is a purpose-built data store for similarity search over high-dimensional vectors.
Unlike relational databases that filter by exact matches, vector databases use approximate nearest
neighbor (ANN) algorithms — such as HNSW (Hierarchical Navigable Small World) or IVF (Inverted
File Index) — to find the most semantically similar vectors in milliseconds, even across millions
of records.

Popular vector databases include:
- Qdrant  : Open-source, written in Rust, supports payload filtering, gRPC and REST APIs.
- Pinecone: Managed cloud service, serverless option available.
- Weaviate: Open-source, supports hybrid search (keyword + vector).
- Chroma  : Lightweight, designed for local development and testing.
- FAISS   : Facebook AI Similarity Search — a library (not a server) for in-process search.

== Embeddings ==

An embedding is a dense numerical vector that captures the semantic meaning of a piece of text.
Texts with similar meanings have vectors that are close together in the high-dimensional embedding
space, measured by cosine similarity or dot product.

Common open-source embedding models:
- nomic-embed-text   : 768-dimensional, runs locally via Ollama, strong multilingual performance.
- all-MiniLM-L6-v2  : 384-dimensional, fast, good for English sentence similarity (HuggingFace).
- mxbai-embed-large : 1024-dimensional, high accuracy, also available via Ollama.
- text-embedding-3  : OpenAI's API-based model, requires an API key.

The embedding dimension determines the vector size used when creating a Qdrant (or other)
collection.  The ingestion and query embedding models MUST be the same, otherwise similarity
search will be meaningless.

== Ollama ==

Ollama is an open-source tool that lets you run large language models locally on your machine
without a GPU (though a GPU will speed things up significantly).  It exposes an OpenAI-compatible
REST API, making it easy to integrate with frameworks like LangChain.

Key Ollama commands:
  ollama serve              — start the Ollama server (usually auto-started)
  ollama pull llama3        — download the Llama-3 8B model
  ollama pull nomic-embed-text — download the embedding model
  ollama list               — list locally available models
  ollama run llama3         — open an interactive chat session

The default Ollama API base URL is http://localhost:11434.
The OpenAI-compatible chat endpoint is: POST /api/chat

== LangChain ==

LangChain is a Python (and TypeScript) framework for building applications powered by language
models.  Its LangChain Expression Language (LCEL) uses the pipe operator (|) to compose chains:

    retriever | format_docs | prompt | llm | output_parser

Key LangChain components used in this RAG system:
- OllamaEmbeddings       : Calls Ollama's embedding API to produce vectors.
- ChatOllama             : Calls Ollama's chat API and returns structured messages.
- InMemoryVectorStore    : In-process vector store for development (no persistence).
- QdrantVectorStore      : Production vector store backed by Qdrant.
- RecursiveCharacterTextSplitter : Splits documents into overlapping chunks.
- ChatPromptTemplate     : Structures the system + human message for the LLM.

== Chunking Strategy ==

Chunking is the process of splitting large documents into smaller passages before embedding.
The chunk size and overlap are critical tuning parameters:

- Chunk size  : The maximum number of characters per chunk (e.g. 500).
  Too small → not enough context per chunk.
  Too large → the embedding averages out too much meaning; also approaches the context limit.

- Chunk overlap : Characters shared between adjacent chunks (e.g. 50).
  Overlap prevents cutting off a sentence or idea at a chunk boundary.

RecursiveCharacterTextSplitter tries to split on paragraph breaks (\n\n), then newlines (\n),
then sentence boundaries (". "), working recursively until chunks are within the size limit.

== System Architecture ==

This RAG system is designed with a swappable retriever pattern:

┌─────────────────────────────────────────────────┐
│  POST /api/query                                │
│       ↓                                         │
│  RagService                                     │
│       ↓           ↓                             │
│  EmbeddingService  IRetriever.get_retriever()   │
│  (OllamaEmbeddings) ↓                           │
│                  MockRetriever  (default)        │
│                  QdrantRetriever (set in .env)   │
│       ↓                                         │
│  PromptBuilder → ChatOllama → StrOutputParser   │
│       ↓                                         │
│  QueryResponse { answer, sources, question }    │
└─────────────────────────────────────────────────┘

Switching from mock to Qdrant requires only:
  1. Set RETRIEVER=qdrant in .env
  2. Set QDRANT_URL to the Qdrant server address
  3. Restart the server

No source code changes are needed.
